# Programmable yt-summary — REST API + MCP Server

**Date:** 2026-05-06
**Status:** Approved for planning
**Owner:** Stefan
**Builds on:** [yt-summary core](2026-05-05-yt-summary-design.md)

## Purpose

Make yt-summary controllable from outside the web UI:

- A REST/JSON API at `/api/v1/*` so that iOS Shortcuts, curl,
  Bookmark managers, n8n, and similar tools can submit videos,
  search the library, fetch summaries, and chat with a video's
  content programmatically.
- An MCP server at `/mcp/sse` so that Claude (Desktop, Code, or any
  other MCP-aware host) can use yt-summary as a tool: "summarize this
  URL", "search my library for X", "what did the speaker say about Y".

Both surfaces share one shared service layer over the existing repos.

## Scope

In:
- `users` table (just one row for now) holding an API key hash and
  metadata. The existing `user_id` columns continue to point at this
  user; the schema groundwork from previous specs becomes a real key.
- API-key generation + display + revoke in Settings.
- API key authentication via `Authorization: Bearer <key>` and
  `X-API-Key: <key>` headers. If no key has been generated yet, the
  API and MCP endpoints accept any request (pragmatic for LAN-only
  self-hosted setups; a clear log warning is emitted at boot).
- REST API: submit, list, get, summary, transcript, search, chat,
  playlists, tags. Async-by-default with optional `?wait=true&timeout=N`
  for synchronous waiting.
- MCP server: HTTP+SSE transport, exposes the same operations as MCP
  tools. Uses the same API key.
- OpenAPI auto-generated by FastAPI at `/api/v1/openapi.json` and
  Swagger-UI at `/api/v1/docs`.

Out (deferred):
- Multi-user auth (login, sessions, role-based access).
- Multi-named API keys (one key per integration with separate audit logs).
- Webhooks / push notifications when summaries are ready.
- OAuth / OIDC.
- Rate limiting (single user on a Pi doesn't need it).

## Data model

New table:

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL DEFAULT 'admin',
    api_key_hash TEXT,
    api_key_prefix TEXT,
    api_key_created_at TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

Migration: on first run, if the table is empty, insert a single row
with `id=1, name='admin'`. Every existing `user_id=1` reference now
points at a real row.

`api_key_hash` is `sha256(api_key).hexdigest()`. The plaintext key
is shown to the user exactly once at generation time; we never store
it.

`api_key_prefix` stores the first 8 chars of the plaintext key for
UI display (`yts_xQ4f...`). Useful for "is the key I'm holding the
same as the one stored?" without revealing anything.

## API key lifecycle

Settings page adds a section:

- **No key set:** "Generate API Key" button. On click, server generates
  32 random bytes, encodes Base32, prepends `yts_` prefix
  (e.g. `yts_xQ4f7Bp9K2HnRtVwXyZa3M6cDeFgHjKL`), stores
  hash+prefix+created_at, returns the plaintext exactly once. UI
  shows a copy-to-clipboard panel with a clear "this is shown only
  once" warning.
- **Key set:** UI shows `yts_xQ4f7Bp9...` (prefix + ellipsis), the
  creation timestamp, and two buttons: "Regenerate" (revokes current,
  creates new, shows once) and "Revoke" (clears hash, future calls
  fall back to the no-key behavior).

Authentication helper (`app/services/auth.py`):

```python
async def authenticate(
    db: aiosqlite.Connection, request: Request
) -> int  # user_id
```

Logic:
1. Read `Authorization: Bearer <token>` or `X-API-Key: <token>`.
2. If a key is configured (a user row has non-null `api_key_hash`),
   require it to match. Mismatch / absent → raise HTTP 401.
3. If no key is configured, return user_id=1 (the default).

A FastAPI `Depends` wrapper handles the lookup; routes that need auth
just declare `current_user_id: int = Depends(authenticate)`.

## REST API

Mounted at `/api/v1/`. JSON request and response bodies. FastAPI's
auto-generated OpenAPI doc at `/api/v1/docs`.

### Endpoints

#### Videos

- **`POST /api/v1/videos`** — Submit a YouTube or article URL.
  Body: `{"url": "..."}`. Query: `wait=false|true` (default false),
  `timeout=N` (seconds, default 60, max 300).

  - Async (`wait=false`): returns `202` with `{"video_id": "...",
    "kind": "youtube|web", "status": "pending|running",
    "summary_ready": false, "url_for_status": "/api/v1/videos/{id}"}`
  - Sync (`wait=true`): returns `200` with the full video resource
    once `summary_ready=true`. If still running after `timeout` seconds,
    returns `202` with the same async-style payload so the caller can
    poll.
  - 400 if URL invalid or article extraction fails.

- **`GET /api/v1/videos`** — List recent videos, paginated.
  Query: `limit=50` (max 200), `offset=0`, optional `tag=`,
  optional `playlist_id=`.
  Returns `{"videos": [...], "total": N}`. Each video is the resource
  defined below.

- **`GET /api/v1/videos/{id}`** — Get a single video's metadata + status.
  Resource:
  ```json
  {
    "id": "abc123...",
    "kind": "youtube",
    "url": "https://...",
    "title": "...",
    "description": "...",
    "thumbnail_url": "/thumbnails/abc123.jpg",
    "duration_seconds": 600,
    "transcript_source": "manual_subs",
    "summary_model": "ollama_chat/gemma4:latest",
    "summary_ready": true,
    "tags": ["python", "fastapi"],
    "playlists": [{"id": "PL...", "title": "Tech"}],
    "job": {"state": "done", "step": "...", "error_message": null,
            "elapsed_seconds": null},
    "created_at": "2026-05-05T15:30:00",
    "updated_at": "..."
  }
  ```

- **`GET /api/v1/videos/{id}/summary`** — Summary as plain Markdown.
  Returns 404 if not yet generated. `Accept: text/plain` returns plain
  text, default JSON wraps it: `{"summary": "...", "model": "..."}`.

- **`GET /api/v1/videos/{id}/transcript`** — Transcript / article body.
  Same shape as summary.

- **`POST /api/v1/videos/{id}/reindex`** — Enqueue a fresh job.
  Returns `202`.

- **`POST /api/v1/videos/{id}/chat`** — Ask a question about the
  video's content. Body: `{"content": "..."}`. Returns
  `{"answer": "...", "history_length": 7}` after the model finishes.
  Synchronous; the API timeout is 120 seconds.

- **`DELETE /api/v1/videos/{id}`** — Out of scope for V1.

#### Search

- **`GET /api/v1/search`** — Hybrid FTS + embedding search.
  Query: `q=...` required, `limit=20`, optional `tag=`.
  Returns `{"hits": [{video resource snipped}, ...]}`.

#### Playlists

- **`GET /api/v1/playlists`** — List user's playlists.
- **`POST /api/v1/playlists`** — Add a playlist URL. Body:
  `{"url": "https://www.youtube.com/playlist?list=..."}`.
  Sync, fetches metadata + initial sync; returns the new playlist.
- **`GET /api/v1/playlists/{id}`** — Detail with linked videos.
- **`POST /api/v1/playlists/{id}/refresh`** — Trigger a sync.
- **`POST /api/v1/playlists/{id}/load-older`** — Pull older entries.
- **`DELETE /api/v1/playlists/{id}`** — Remove (CASCADE deletes links).

#### Tags

- **`GET /api/v1/tags`** — All tags + their video counts.

#### Health

- **`GET /api/v1/health`** — `{"ok": true, "version": "0.3.0"}`. No auth.

### Response conventions

- Errors: `{"error": "human-readable string", "code": "STRING_CODE"}`.
- Timestamps: ISO-8601 in UTC.
- IDs: opaque strings; do not parse format.
- Status codes: 200 OK, 201 Created, 202 Accepted (async), 400 invalid
  input, 401 unauthorized, 404 not found, 429 reserved (not currently
  enforced), 500 server error.

## MCP Server

Mounted at `/mcp/sse` (HTTP+SSE transport). Uses the official `mcp`
Python package's FastAPI integration. Authenticates via the same API
key as the REST API.

### Tools

- **`submit_url(url, wait_for_summary=False, timeout=120)`** —
  Returns `{video_id, summary_ready, summary?, status}`.
  When `wait_for_summary=True`, blocks up to `timeout` seconds and
  returns the summary inline if ready.

- **`search(query, limit=10)`** — Returns top hits. Each hit:
  `{video_id, title, url, summary_excerpt (200 chars), score}`.

- **`get_summary(video_id)`** — Returns full summary markdown or
  raises `not_found`.

- **`get_transcript(video_id)`** — Returns full transcript / article
  body.

- **`ask_video(video_id, question)`** — Returns the assistant's
  answer text. Synchronous. Persists the user+assistant turn into
  the same chat history that the web UI shows, so a thread carries
  across MCP and UI use.

- **`list_recent(limit=20, tag=None)`** — Returns recent videos
  (lightweight resource).

### Why these tools and not more

The MCP-tools are deliberately minimal so Claude doesn't drown in
choices. Anything that's purely management-flavored (delete, settings,
playlist administration) stays REST-only — Claude rarely needs it.

### Transport

`/mcp/sse` is the standard MCP-over-SSE endpoint. Claude Desktop's
config:

```json
{
  "mcpServers": {
    "yt-summary": {
      "command": "npx",
      "args": [
        "-y",
        "mcp-remote",
        "http://your-pi.local:8200/mcp/sse",
        "--header",
        "Authorization: Bearer yts_..."
      ]
    }
  }
}
```

(`mcp-remote` is a small npm-installable adapter that bridges
stdio-MCP-clients to HTTP/SSE servers. Claude Desktop's stable
release as of writing speaks stdio only; `mcp-remote` solves that.
Claude Code (the CLI) and other newer MCP hosts can speak HTTP/SSE
directly and don't need the adapter.)

## Architecture

```
                          ┌─────────────┐
                          │ Settings UI │
                          │  (gen key)  │
                          └──────┬──────┘
                                 │
          ┌──────────────────────┴─────────────────────┐
          │                                            │
          ▼                                            ▼
   ┌─────────────┐                            ┌────────────────┐
   │ /api/v1/*   │                            │   /mcp/sse     │
   │ FastAPI     │                            │   MCP-over-SSE │
   │ JSON in/out │                            │                │
   └──────┬──────┘                            └────────┬───────┘
          │                                            │
          └──────────────┬─────────────────────────────┘
                         ▼
                ┌────────────────────┐
                │ services/api.py    │  ← shared business logic
                │ (submit_video,     │
                │  ask_video, ...)   │
                └────────┬───────────┘
                         ▼
        ┌────────────────────────────────────┐
        │ Existing repos + services           │
        │ (videos, summarizer, chat, ...)    │
        └────────────────────────────────────┘
```

`services/api.py` is the new shared layer. Both `routes/api.py` and
`routes/mcp.py` only translate between protocol and this shared
layer — no business logic in either route module.

## Components

### `app/repos/users.py` (new)

```python
async def get_default_user(db) -> User
async def set_api_key(db, user_id, *, key_hash, key_prefix) -> None
async def clear_api_key(db, user_id) -> None
async def find_by_api_key_hash(db, key_hash) -> User | None
```

### `app/services/auth.py` (new)

`generate_api_key() -> tuple[plaintext, hash, prefix]` — module-level
helper. The Settings route calls this once and shows the plaintext.

`async def authenticate(db, request) -> int` — FastAPI dependency.

### `app/services/api.py` (new)

Aggregates the existing pieces into one user-scoped facade:

```python
async def submit_video(db, config, *, url, user_id, wait, timeout) -> SubmitResult
async def get_video_resource(db, video_id) -> VideoResource | None
async def list_videos(db, limit, offset, tag, playlist_id) -> list[VideoResource]
async def search_videos(db, query, limit, tag) -> list[VideoResource]
async def chat_about_video(db, video_id, content, user_id) -> ChatResult
# ... and so on
```

These are thin orchestrators of existing repo + service calls, but
they're useful because the request-side adapters become trivial.

### `app/routes/api.py` (new)

A FastAPI sub-router mounted at `/api/v1`. Each handler calls
`authenticate` first, then delegates to `services/api.py`.

### `app/routes/mcp.py` (new)

Mounts the MCP server at `/mcp/sse`. Each MCP tool is a thin async
function that calls into `services/api.py`. The `mcp` Python package
handles the SSE protocol, tool registration, and JSON-Schema-from-type-hints.

## Sync vs Async submit (clarification)

`POST /api/v1/videos` async-by-default. With `wait=true`, the handler
polls the `videos.summary` field every 1s until it's set or the
timeout hits. Polling is in-process; the actual work runs in the
existing job worker as today. No new background machinery.

The 300-second cap on `timeout` exists because Whisper + map-reduce
can take that long on the Pi, and we want to free the connection
slot. Beyond that the caller has to use async + poll.

## Error handling

- API key wrong → 401 with code `INVALID_API_KEY`
- URL fails to import → 400 with code `IMPORT_FAILED` and the underlying
  reader's message
- Video id not found → 404 with code `NOT_FOUND`
- Sync wait times out → 202 with code `STILL_PROCESSING`, payload includes
  `video_id` so caller can switch to polling
- LLM unconfigured for chat → 400 with code `LLM_NOT_CONFIGURED`
- MCP tool errors propagate as MCP error frames with the same codes
